Hi everyone. Right now our cube spins only because we set it up in the editor, and none of the logic is coming from code yet. I want to change that today. So I start with a blank script, and we write the first real lines together. A few mistakes will show up along the way, and those mistakes are where most of the learning happens. If you have never typed a line of C sharp before, you are in the right place. We will keep every step small, so you can follow along line by line. Before we start, it helps to know why any of this matters. A script is how our own logic meets the engine, and every game is built from a surprising number of these small pieces. I learned that the hard way, because my early projects had everything squeezed into one file. We will keep the code short, and I'll explain the reason behind each line. You won't need to memorise anything, because we rebuild each idea from scratch as we go.

Here is the script we created earlier. It has two default methods, Start and Update, and both are empty right now. We can see that Start is called once, when the object first appears, and Update is called once per frame. We don't need anything from Start yet, so we leave it alone. Everything interesting happens inside Update, and that's where we focus. Both of those methods are generated by Unity, so we don't have to type them ourselves. Unity looks for them by name, which is why the names matter so much. If you spell Update with a small u, the engine simply ignores the method, and nothing happens at all. I tried that once, and I still remember the cube sitting there doing nothing for 10 minutes. We probably should have checked the spelling first, because a quick look at the console would have shown that the method was never called. Before we write any logic, we check that the script is attached to the cube and that the console window is open on the screen.

The first line is the simplest one we can write. Inside Update, we type Debug dot Log, and in the brackets we put a short message in quotes. We save the file and return to Unity. The console shows the message, and it appears again on every single frame. That's a useful reminder of how often Update runs. The console has a second use that we need to know about now. Every message is time stamped, and messages come in 3 kinds, with warnings and errors shown in different colours. For example, a yellow warning does not stop the game, while a red error usually does. I rely on that difference constantly, because it tells me what to fix first. If the list gets long, the buttons at the top can filter it down, and I find that keeps the view calm. It's also a little overwhelming, so we remove the line once we have confirmed that it works. Nothing is lost by doing that, and the console stays readable.

Now we need something to store a value. A variable is a named box that holds a piece of data. We write float speed equals 90, and the word float tells the compiler that this box holds a decimal number. The type matters because the compiler checks every operation against it. Types come in several flavours. An int holds whole numbers, a float holds decimal numbers, and a string holds text. We pick the type that matches the job, because the compiler then checks our work for us. I like the way the compiler keeps us honest, and I've seen it save hours. We might see a complaint about a float that was never marked as one, and the fix is usually obvious once we read the message. If we later try to put a piece of text into the speed box, the compiler stops us before anything runs. That early check saves a lot of time, and we will rely on it again soon.

The speed variable is going to control how fast the cube turns. But there's a catch. Update runs once per frame, and frames don't all take the same amount of time. On a fast computer, Update might run 120 times a second, and on a slower one it might run 30 times. If we rotate by a fixed amount each frame, the cube would spin faster on the faster machine. To fix that, we multiply by Time dot deltaTime, which is the time in seconds since the last frame. That single multiplication makes the motion the same on every machine. Let's think about the numbers for a moment. If a computer runs at 60 frames per second, each frame lasts about 0.0167 seconds. We multiply the speed by that small number, so the rotation per frame is small. Over one second, the same speed adds up to the same total, whatever the frame rate. You can test this yourself by changing the frame rate, and you will see the same result. We check that often, because it's the real purpose of delta time.

So the rotation line becomes transform dot Rotate, with a vector that points around the y axis, multiplied by speed and by delta time. We write it out in full, and then we check the units. Speed is in degrees per second, delta time is in seconds, so the product is degrees for this frame. The units cancel the way we want. This is simple maths, but getting it right is what makes the motion identical everywhere. For example, a speed of 90 with a delta time of 0 point 5 gives 45 degrees in that step.

We save the file and press play. The cube spins at 90 degrees per second, which is a quarter turn each second. We can check that with a stopwatch, and it's close enough for our purposes. If the cube looks too slow, we make the number bigger. If it looks too fast, we make it smaller. The result depends entirely on the value in the box, which is the whole point of having a variable. Changing one number changes the whole behaviour, and nothing else has to move.

Now for a deliberate mistake, because they happen all the time. I removed the semicolon at the end of the Debug line and pressed save. Unity immediately shows a red error in the console, and the message says that a semicolon is expected. The line number is usually right, so we go to it, add the missing character, and save again. The error disappears. Reading the message carefully is the fastest way to fix most problems, so it's worth doing it every time, even when the fix looks obvious.

With the script working, we can tune it without touching the code. We select the cube, and the inspector shows the public speed field. Because the variable is public, Unity exposes it there. We can change the value while the game is running, and the cube responds straight away. This is a useful workflow for tuning, because we don't need to stop, edit, recompile and restart each time. We drag the number up or down until it feels right, and then we copy the final value back into the code if we want to keep it.

To make the point clearly, we add a second cube and give it the same script. Both cubes now run identical code, but each has its own speed value in the inspector. One can be set to 30, and the other to 200. The result is two cubes spinning at very different rates, from a single piece of code. This is the pattern we use across the whole project. Code defines the behaviour, and the editor supplies the numbers. Once that idea clicks, a lot of the editor starts to make more sense. One more useful habit is to name things clearly. A variable called speed is much easier to read than a variable called s. We can give the second cube a field called spin speed if it helps, and we keep the same convention across the project. I prefer names that describe the value rather than the type, because the type is already visible in the code. You come back to these names later, so it's worth choosing them carefully. I think that habit pays off faster than most people expect.

Let's look at what the script actually does now. It stores a speed, it reads the time since the last frame, and it turns the transform each time Update runs. That's three ideas, and each one is small. The variable holds a value, the delta time makes the motion independent of frame rate, and the rotation applies the change. Nothing about it is clever, but it's the foundation for almost every behaviour in a game, and the same shape appears again and again.

It's worth noticing how little code was needed. The whole script is a handful of lines, and most of them are about getting the units right. Writing code in a game is often less about complicated algorithms and more about making sure every number means what we think it means. We keep an eye on units, we check our assumptions, and we fix the errors the console tells us about. That habit matters more than any single trick, and it's probably the most useful thing to practise early on.

One caveat before we finish. The Debug log and the rotation are both simple, and real games quickly grow beyond a single file. There is a limit to how far one script can go before it becomes hard to read. I suspect most people hit that limit sooner than they expect, and that's a good moment to start thinking about structure. For now, though, one script with three ideas is exactly the right size.

In the next episode, the focus moves to classes, which are the containers that hold scripts like this one together. I expect it to feel more abstract at first, but the examples will stay small, and I'm confident we can make it concrete quickly. I'm curious how the speed field will look once it becomes part of a larger structure.
